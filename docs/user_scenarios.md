# Пользовательские сценарии

## Сценарий 1. Вход в систему

| Пункт | Описание |
|---|---|
| Кто выполняет | Любой зарегистрированный пользователь |
| Проверяются данные | Имя пользователя, пароль, активность учетной записи |
| Логируется | Успешный вход в `audit_logs`, неуспешный вход в `audit_logs` и `login_attempt_logs` |
| Ошибка | 401 при неверных данных, 403 при отключенной учетной записи, 429 при блокировке |
| Запрещено | Вход отключенного пользователя |

## Сценарий 2. Создание сетевого события

| Пункт | Описание |
|---|---|
| Кто выполняет | `admin`, `security_engineer`, `operator` |
| Проверяются данные | Узел, правило, IP-адреса, протокол, тип события, критичность, XSS-маркеры |
| Логируется | Создание события в `audit_logs` |
| Результат | Рассчитываются `risk_score`, `risk_level`, `detection_reason` |
| Ошибка | 404 при неизвестном узле/правиле, 422 при некорректном вводе |

## Сценарий 3. Просмотр событий

| Пункт | Описание |
|---|---|
| Кто выполняет | Авторизованный пользователь |
| Доступ | `admin` и `security_engineer` видят все, `operator` видит свои и явно выданные события |
| Логируется | Не логируется как чтение |
| Ошибка | 403 при попытке открыть чужое событие |
| Запрещено | Прямой доступ к чужому событию без grant |

## Сценарий 4. Запуск анализа

| Пункт | Описание |
|---|---|
| Кто выполняет | `admin`, `security_engineer` |
| Проверяются данные | JWT и роль |
| Логируется | `run_analysis` |
| Результат | Обновление риска и создание/обновление correlation alerts |
| Ошибка | 403 для `operator` |

## Сценарий 5. Создание инцидента из alert

| Пункт | Описание |
|---|---|
| Кто выполняет | `admin`, `security_engineer` |
| Проверяются данные | Существование alert и связанных событий |
| Логируется | `create_incident_from_alert` |
| Результат | Создается incident, повторный запрос возвращает уже созданный incident |
| Ошибка | 404 при неизвестном alert, 400 если нет связанных событий |

## Сценарий 6. Управление пользователями

| Пункт | Описание |
|---|---|
| Кто выполняет | `admin` |
| Проверяются данные | Email, роль, статус активности |
| Логируется | `update` или `delete` для сущности `users` |
| Результат | Смена роли или отключение учетной записи |
| Запрещено | Отключить самого себя, снять с себя роль `admin` |

## Сценарий 7. Импорт CSV

| Пункт | Описание |
|---|---|
| Кто выполняет | `admin`, `security_engineer` |
| Проверяются данные | CSV-поля, enum-значения, timestamp |
| Логируется | `import_dataset` |
| Результат | Создаются события, неизвестный узел создается как `server` |
| Ошибка | Ошибка парсинга CSV или недопустимые значения |

## Сценарий 8. Проверка опасного ввода

| Пункт | Описание |
|---|---|
| Кто выполняет | Любой пользователь через формы/API |
| Проверяются данные | SQLi-подобные строки и XSS-паттерны |
| Логируется | Неуспешный вход логируется; невалидные формы возвращают 422 |
| Результат | SQLi не расширяет выборку, XSS-паттерны отклоняются |
| Ошибка | 401/422 без раскрытия stack trace |
