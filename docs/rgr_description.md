# Описание РГР

## Цель системы

Цель системы - разработать программный комплекс для обнаружения подозрительной активности в сети связи на основе анализа сетевых событий. Система должна не только хранить события, но и автоматически оценивать риск, объяснять причину подозрительности, выявлять корреляционные признаки атак и помогать формировать инциденты безопасности.

## Предметная область

Предметная область - мониторинг сетевой инфраструктуры оператора связи. В ней присутствуют RADIUS/AAA-серверы, BRAS, SBC, DNS, NMS, firewall, gateway, router, BSC и LTE base station. События отражают ошибки аутентификации, сканирование портов, всплески трафика, несанкционированный доступ, изменения конфигурации и потерю связи с узлами.

## Модель данных

Основные сущности:

- `users`: пользователи системы с ролями `admin`, `security_engineer`, `operator`;
- `network_nodes`: сетевые узлы связи;
- `network_events`: события с параметрами источника, назначения, протокола, типа, критичности и рассчитанного риска;
- `detection_rules`: правила обнаружения с весом риска, временным окном и порогом количества;
- `correlation_alerts`: результаты корреляционного анализа;
- `correlation_alert_events`: связь alert и событий;
- `incidents`: инциденты безопасности, в том числе созданные из correlation alert;
- `audit_logs`: журнал действий пользователей.

В `network_events` добавлены поля `risk_score`, `risk_level`, `detection_reason`, `analyzed_at`. В `incidents` добавлено поле `correlation_alert_id`.

## Алгоритм обнаружения подозрительной активности

Алгоритм выполняется при создании или обновлении события:

1. Загружается связанный сетевой узел.
2. По таблицам весов оцениваются `severity`, `event_type`, `protocol`, внешний `source_ip` и `node_type`.
3. Активные `detection_rules` с тем же `event_type` добавляют свой `risk_weight`.
4. Итог ограничивается значением 100.
5. По итоговому баллу определяется `risk_level`.
6. Если `risk_score >= 50`, событие получает `is_suspicious=true`.
7. Формируется `detection_reason` на русском языке.
8. Запускается корреляция события с другими событиями за последние 10 минут.

## Формула risk_score

Общая формула:

```text
risk_score = min(
  100,
  severity_weight
  + event_type_weight
  + protocol_weight
  + source_ip_weight
  + node_type_weight
  + sum(active_rule.risk_weight)
)
```

Переход к уровню риска:

- `0-24`: `low`;
- `25-49`: `medium`;
- `50-74`: `high`;
- `75-100`: `critical`.

Пример: событие `port_scan` с внешнего `203.0.113.x` на `firewall`, `severity=high`, `protocol=TCP`:

```text
50 + 35 + 5 + 20 + 15 = 125 -> 100
```

Итог: `risk_score=100`, `risk_level=critical`, `is_suspicious=true`.

## Правила корреляции

1. Множественные ошибки аутентификации: 5 и более `auth_failed` с одного IP за 10 минут.
2. Сканирование сетевой инфраструктуры: 3 и более `port_scan` с одного IP за 10 минут или обращения к разным `destination_ip`.
3. Аномальный рост трафика на критическом узле: `traffic_spike` на `firewall`, `gateway`, `router`.
4. Подозрительный внешний доступ: внешний IP обращается к `server`, `firewall`, `gateway` или NMS с типом `unauthorized_access` или `suspicious_ip`.

Каждое правило создает или обновляет `correlation_alert`. Повторный запуск анализа не дублирует активные alert с тем же названием, источником и узлом.

## Сценарии тестирования

Проверяются следующие сценарии:

- корректный расчет `risk_score`;
- определение `risk_level`;
- установка `is_suspicious=true` при `risk_score >= 50`;
- создание alert при 5 `auth_failed` с одного IP;
- создание alert при `port_scan`;
- создание incident из alert;
- запрет повторного incident из одного alert;
- запрет удаления alert для `operator`;
- запуск анализа пользователем `security_engineer`;
- импорт CSV и создание `network_events`.

## Ожидаемые результаты

После запуска seed-данные должны создать реалистичную демонстрационную базу: 10 узлов, 10 правил, 50 событий, 15 инцидентов и не менее 10 correlation alerts. На frontend должны отображаться риск события, распределение риска, топ источников, динамика событий, alerts и импорт dataset.

Для события с высоким риском пользователь видит числовой балл, уровень риска, причину обнаружения и связанные alerts/incidents. Для correlation alert пользователь может изменить статус или создать incident.

## Ограничения системы

- Алгоритм основан на экспертных правилах и статических весах.
- Нет потоковой обработки событий в реальном времени.
- Нет ML-модели и обучения на исторических данных.
- Корреляция использует простое временное окно и ограниченный набор сценариев.
- Импорт CSV создает неизвестный узел как `server`, если `node_name` не найден.

## Пути развития

- Добавить потоковую обработку событий через Kafka или Redis Streams.
- Хранить профили нормального поведения узлов и абонентских сегментов.
- Добавить ML/anomaly detection для трафика и DNS.
- Расширить корреляцию MITRE ATT&CK-подобными цепочками.
- Добавить SLA, приоритеты и назначение ответственных групп.
- Внедрить Alembic для полноценных миграций БД.
- Добавить интеграции с SIEM, syslog, NetFlow/IPFIX и SNMP traps.
